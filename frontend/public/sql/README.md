# HealthPulse SQL showcase

Three inspectable MySQL 8 SELECT statements explore synthetic insurance premiums and related claims. The regular dashboard executes these queries on the full MySQL database. The published demo uses saved full-source results across 5,000,000 members, 4,499,910 enrollments, 13,179,693 claims, and 9,710,863 diagnosis records. Only the table browser is limited to a connected 200-member sample.

The saved results were originally generated from all records in four source CSVs projected into SQLite. On October 6, 2026, all three statements were executed on the full local MySQL 8.0.45 database. Their complete result checksums match the saved results exactly, with the same parameters and table counts. The original generation engine and date are preserved; MySQL verification is recorded separately. This verifies these SELECT results, not every field in the database or the runtime of the complete API.

## Reproduce the saved results

From the backend directory, run `venv/bin/python export_full_sql.py` (or `venv/bin/python sql_showcase.py`) to rebuild the full-source results, and `venv/bin/python -m unittest test_sql_showcase` for boundary and grain tests. Inputs are the four source CSVs and `frontend/public/demo/snapshot.json`. Other summaries and date metadata are preserved. Rebuild the demo after updating results. A projected database under `/private/tmp/healthpulse-premium-source.sqlite` can be reused when the source signatures match; it is never included in the deployment.

When MySQL is available, the regular dashboard's Premium Equity & SQL tab reads `/api/stats/premium-equity` and can change the coverage cutoff and claims interval. `venv/bin/python run_sql_showcase_mysql.py` also executes the statements in a read-only transaction and prints results without changing the snapshot. `venv/bin/python export_demo.py` refreshes the saved full-MySQL results alongside other demo data. The three SELECTs are now verified on MySQL; the complete API runtime was not measured by this study.

Parameters: `as_of = 2025-11-30`, `claims_start = 2024-11-01`, `claims_end = 2025-12-01` (exclusive), `minimum_peers = 2`. Named placeholders use SQLAlchemy parameter binding. For MySQL Workbench, bind the same values through session variables and replace named placeholders with the matching variables. Do not interpolate user input into SQL.

## Questions, grain, and controls

1. **Regional premiums:** one eligible ENROLLMENT row is the unit. Active means start date on or before the cutoff and end date on or after it, or NULL. Include nonnegative recorded premiums. The calculation divides each premium by its plan-and-tier mean, including itself, then averages ratios by state. The applied SQL first groups by state, plan, and tier, computes peer means from summed premiums and enrollment counts, and preserves the original enrollment weights. Exclude peer cells smaller than two and zero-mean cells. Index 100 is the peer mean. The browser defaults to all returned states; changing the minimum displayed-state count preserves the original peer calculations. DENSE_RANK reflects all returned states, even when the display hides smaller states.
2. **Housing insecurity:** one member with an eligible linked enrollment and known housing status is the unit. Only plan-and-tier cells containing both groups contribute. Conditional aggregation computes two cell means. Each group receives identical cell weights equal to the smaller group count. The result is a common-mix descriptive difference, not an estimate controlled for age, state, health, or selection into a plan. Shared enrollment premiums can be repeated across linked members, intentionally creating member weights rather than enrollment weights.
3. **Conditions and costs:** one member with an eligible linked enrollment is the unit. Count DISTINCT condition IDs diagnosed by the cutoff, and separately aggregate claims in the fixed interval. Join these one-row-per-member aggregates using LEFT JOIN. This avoids multiplying claims by diagnosis records and preserves zero-claim members in the denominator. Zero recorded diagnoses is not proof of no disease. The linked enrollment is not a reconstructed enrollment history for each claim. Diagnosis information by the end of the period is descriptive, not a prospective risk score.

The premium billing period is undocumented, so recorded premiums are not annualized and no claims-to-premium loss ratio is reported. Income and pricing-algorithm outputs are unavailable. Housing insecurity is not income. Synthetic disparities do not demonstrate real discrimination, affordability, clinical effects, or algorithmic fairness. Small groups are shown with counts instead of inferential claims.

## Validation evidence

Full-result eligible member counts and claim totals reconcile with direct joins, and the weighted regional premium index reconciles to 100. SQL logic is independently recomputed on the connected sample using Python dictionaries and groups. Boundary tests check repeated diagnoses on different dates, multiple claims, future diagnoses, claim interval boundaries, coverage end-date boundaries, zero claims, zero premiums, empty data, unmatched enrollment links, unavailable comparison groups, and unequal group counts. These are logic and aggregate checks, not an independent full-population recomputation of every output. SQL files are hashed into the snapshot so build checks detect divergence between downloaded queries and saved definitions.

## MySQL query-plan and timing study

The baseline was measured on October 6, 2026, at 10:46 AM America/Chicago: local MySQL 8.0.45, 32,400,574 records across eight tables, one client, three repeated direct reads per query. Median times were 0.826 ms for member lookup, 1.052 ms for the first table page, 3.235 s for monthly claims, 17.760 s for regional premiums, 16.524 s for housing comparisons, and 36.466 s for conditions and costs. All ten workloads, SQL, parameters, existing indexes, result checksums, and plans are retained in [the measurement report](../benchmarks/mysql-performance.json). These are baseline timings, not a measured optimization gain.

Run `venv/bin/python benchmark_mysql.py` from the backend folder in your own Terminal. This measures the main dashboard's seven SELECT workloads and the three premium queries on the full MySQL database, using shared dashboard statements rather than the public demo. It saves `backend/benchmarks/mysql-performance.json` with exact counts, SQL, parameters, existing indexes, EXPLAIN ANALYZE plans, first-read times, and medians of three repeated uncached reads. Returned result checksums must agree across repeats. Timing includes fetching database results and excludes application caching, HTTP, and browser rendering. Metadata and counts are read first, and database buffers are not flushed, so first-read times are not cold-disk measurements. No data or indexes are changed. The successful report was produced from the user's Terminal. The authoring session cannot directly connect under its current access policy.

1. Record MySQL version, row counts, exact parameters, existing indexes, machine configuration, and concurrent load. Use a read-only benchmark database or replica with the same schema and data when possible.
2. Run each SELECT and reconcile its eligible counts and totals first. Run EXPLAIN ANALYZE on the same SELECT with the same bound values. It executes the query; record actual rows, loops, iterator times, and access paths.
3. Inspect existing indexes before proposing changes. The schema already includes CLAIMS(member_id, date), MEMBER_CONDITION(Member_ID, Condition_ID, Diagnostic_date), and MEMBERS(Enrollment_ID). A claims date filter without a member predicate may justify testing a date-leading covering index on CLAIMS(date, member_id, amount), subject to selectivity, storage, and write costs. It is a candidate, not an installed or validated improvement.
4. If index changes are authorized on the benchmark database, repeat the plan and timing study on the same data. Run several comparable trials, separate cold and warm runs, and record median times and result equality. Do not attribute an application-cache hit to an index speedup.
5. Retain before/after plans and timings beside the query. Report regressions and tradeoffs as well as improvements. SQLite timings cannot substitute for MySQL measurements on the full dataset.

Official reference: https://dev.mysql.com/doc/refman/8.0/en/explain.html


## Candidate query improvements

Run `venv/bin/python compare_mysql.py` from the backend directory. This compares current regional and conditions queries against three candidates in a single read-only consistent snapshot, alternating execution order. It saves `benchmarks/mysql-optimization.json` only when every candidate returns the same complete result checksum as its baseline. It records fresh baseline and candidate timings and EXPLAIN ANALYZE plans. No records, indexes, or dashboard SQL are changed. Expect several minutes for the full comparison.

The regional candidate groups eligible enrollments by state, plan, and tier before applying window calculations, retaining enrollment weights and the same ranking. The baseline plan buffered approximately 3.15 million eligible records. The conditions candidates test existing primary index scans to avoid the diagnosis date-index scan followed by sorting, and to test a clustered claims scan instead of fetching amounts through a noncovering secondary index. The October 6, 2026 comparison verified equal complete result checksums for all candidates on MySQL. The regional median fell from 17.774 s to 7.482 s, a 57.91% reduction and 2.376 times speedup. Every repeated candidate read was faster than every repeated reference read. Its window inputs fell from approximately 3.15 million records to 8,000 grouped cells. That rewrite is applied to the regular dashboard and downloadable SQL; its saved output is unchanged. The diagnosis scan candidate improved 4.60%, with overlapping trial ranges; the two-scan candidate was 2.20% slower. Neither conditions hint is applied. Three paired repeats support this local fixed-period comparison, not a many-client or Cloud SQL performance claim. The original regional SQL is retained under `baselines/regional_premiums.sql`, and [all successful and unsuccessful comparisons](../benchmarks/mysql-optimization.json) include plans and timings.

Index selection and GROUP BY costs are explained in the [MySQL GROUP BY optimization documentation](https://dev.mysql.com/doc/refman/8.0/en/group-by-optimization.html). The covering claims index was subsequently tested and activated as described below; storage and write costs remain to assess. No speedup is inferred from fixture timings or application-cache hits.


## Covering claims index experiment

The conditions query remains unchanged. From the backend folder, run `HEALTHPULSE_CREATE_COVERING_INDEX=1 venv/bin/python benchmark_covering_index.py` to test a covering CLAIMS(member_id, date, amount) index. This explicitly adds an invisible index if no identical one exists, using INPLACE and LOCK=NONE. It consumes storage, adds index maintenance work, and may take several minutes to build. Stored records are unchanged. The index remains installed even if the benchmark fails; the script does not drop indexes or make an invisible index visible.

The experiment compares the existing member/date claims index with the covering index in alternating read-only trials on the full data. Invisible indexes are enabled only in this benchmark session; normal sessions retain their existing index choices. It saves `benchmarks/mysql-covering-index.json`, including creation time separately from query timings, exact SQL and plans, and result equality checks. It does not promote the new scan or publish an improvement automatically. Reuse of an existing matching index avoids duplicate creation. Running without the explicit environment setting refuses to create a missing index.

See [MySQL invisible indexes](https://dev.mysql.com/doc/refman/8.0/en/invisible-indexes.html) and [CREATE INDEX](https://dev.mysql.com/doc/refman/8.0/en/create-index.html) for the supported mechanisms. The user completed this trial on local MySQL 8.0.45 on October 6, 2026 at 12:12 PM America/Chicago. Three paired repeated reads measured 38.189 s with the existing claims index versus 23.446 s with the covering index, a 38.60% time reduction and 1.629 times speedup, with identical full-data results. Index construction took 6.061 s separately. [The paired trial report](../benchmarks/mysql-covering-index.json) retains exact SQL, plans, counts, parameters, and timings.

Activation completed at 12:28 PM. The index is visible to normal queries. MySQL selected it for the unchanged dashboard SELECT without index hints, and the median of three repeated reads was 18.917 s. All results matched the full-data baseline. This later activation check is not a fresh paired comparison and does not establish a 38.189 to 18.917 s paired speedup. [The activation report](../benchmarks/mysql-covering-index-applied.json) preserves its normal SQL and plan. Timing excludes HTTP, caching, and browser rendering. Storage and write overhead have not been measured.
